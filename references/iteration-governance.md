# Skill 迭代与规则一致性

## 为什么保存过程

用户对试写的连续反馈不仅给出最终偏好，还暴露错误是怎样产生的。例如：内容过薄 → 误把字数设成硬门槛 → 改用对白撑时长 → 对白拖沓 → 认识到动作与对白应共同承担可演过程。只保存最后一句“多写动作”，下一次仍可能从另一个方向犯同类错误。

因此，提炼时同时记录最初症状、采用过的修法、修法产生的新问题、用户的后续修正、最终上位原则，以及原问题与反向问题的测试方法。

## 更新前先分类

收到新反馈后，不要直接追加条目。先判断它与现有规则的关系：

- **替换**：新认识证明旧规则错误；删除旧规则，用新规则取代。
- **修正**：方向仍对，但表述过窄、过宽或因果错误；重写原规则。
- **限定**：规则只在特定题材、场景或条件成立；把适用条件写回原处。
- **补充**：覆盖此前没有处理的新维度；新增规则并连接相关流程。
- **举例**：只帮助理解，不具备普遍约束力；放入案例或参考，不升级为通则。

若暂时无法判断，标为待验证，不要提升为强规则。

## 建立唯一判断来源

同一原则只在一个最合适的位置保存完整版本；其他文件只链接或写极短提醒。避免在 SKILL.md、质量表、病例库和模板里复制多套略有不同的表述。

规则冲突时按以下顺序处理：

1. 用户对当前作品的明确决定；
2. 已确认且仍有效的核心人物、关系、世界规则和商业方向；
3. “讲一个好故事”以及人物、因果成立等高层原则；
4. 题材与场景相关的方法；
5. 时长、字数、节拍、卡点等经验性启发；
6. 单个好坏案例。

低层启发不得推翻高层原则。案例用于发现机制，不作为所有作品都必须遵守的格式。

## 冲突审计

每次更新前后检查：

- 新规则是否与旧规则要求相反；
- 两条规则是否只是同义重复；
- 是否仍残留已被用户否定的绝对词，如“必须达到”“一律禁止”；
- 经验区间是否被误写成硬门槛；
- 特定案例是否被扩大为全部题材的通则；
- 新规则是否改变工作阶段、确认权限或核心优先级；
- 参考文件与 SKILL.md 的路由是否一致。

发现冲突时，不要继续增加例外说明来勉强兼容；回到共同上位目标，重写成一条能解释两种情况的规则，并删除失效句。

## 防止过度纠偏

任何修正都做双向测试：

- **原问题测试**：新规则能否阻止最初的失败？
- **反向问题测试**：新规则是否会把作品推向相反极端？

例如：防止剧本过薄，不能演变为固定字数注水；防止对白注水，不能演变为无声动作堆砌；防止系统代办剧情，不能演变为系统完全失去戏剧功能；强调强卡点，不能演变为每集都靠突发来报；强调现代化对白，不能抹掉人物时代、身份和个人声纹。

## 一轮完整迭代

1. 保存用户原始判断和对应产物。
2. 定位问题层级：语言、呈现、场景、分集、情节或全剧结构。
3. 追溯产生问题的旧规则或隐含假设。
4. 分类为替换、修正、限定、补充或举例。
5. 在唯一来源处改写规则，删除冲突和重复表述。
6. 更新质量复检或失败模式，但不复制整段规则。
7. 用原问题与反向问题各做一次回归测试。
8. 校验文件结构、引用与 Skill 元数据。
9. 记录用户仍未确认的判断，不擅自固化。
